## What is wrong

Five hooks build GitHub REST URLs by raw template interpolation. No hook calls
`encodeURIComponent`:

| Hook | Constructed URL | Untrusted source |
|---|---|---|
| [`useFetchUserData.ts:13`](../../client/src/hooks/useFetchUserData.ts#L13) | `api.github.com/users/${username}` | route param |
| [`useFetchRepositories.ts:9`](../../client/src/hooks/useFetchRepositories.ts#L9) | `api.github.com/users/${username}` | route param |
| [`useFetchReposPerPage.ts:22`](../../client/src/hooks/useFetchReposPerPage.ts#L22) | `api.github.com/users/${username}/repos?per_page=8&page=${page}` | route param |
| [`useShowIndividualRepo.ts:21`](../../client/src/hooks/useShowIndividualRepo.ts#L21) | `api.github.com/repos/${username}/${repoName}` | route params |
| [`useFetchSearchUsers.ts:16`](../../client/src/hooks/useFetchSearchUsers.ts#L16) | `api.github.com/search/users?q=${query}` | `?query=` search param |
| [`useInfiniteUsers.ts:19`](../../client/src/hooks/useInfiniteUsers.ts#L19) | `api.github.com/search/users?q=${query}&page=…` | `?query=` search param |

### 3a. Path segment escape → arbitrary GitHub API endpoint

React Router decodes path params, so `%2F` becomes a real `/`, and the WHATWG
URL parser then **normalises `..` segments before the request is sent**.

Visit:

```
/user/x%2F..%2F..%2Forgs%2Fgithub
```

`username` decodes to `x/../../orgs/github`, producing:

```
https://api.github.com/users/x/../../orgs/github
        → normalised → https://api.github.com/orgs/github
```

The request goes to an endpoint the developer never intended — **with the
`Authorization` header still attached**. Reachable targets include
`/user` (the token owner's own profile), `/user/repos` (private repos, if the
token is scoped), `/notifications`, and `/user/emails`. This is a
client-side analogue of SSRF: the attacker steers an authenticated request.

Combined with [01](01.exposed-github-token.md) the attacker already has the
token, so today this mainly matters as *the same bug that will still be there
after you fix 01*. Behind a proxy it becomes the primary escape hatch.

### 3b. Query-parameter injection in search

`?query=` is interpolated into `q=${query}` with no encoding, so `&` starts a
new parameter:

```
/explore?query=a%26per_page=100%26sort=followers
→ https://api.github.com/search/users?q=a&per_page=100&sort=followers&page=1&per_page=20
```

The attacker controls `sort`, `order`, and an *earlier* `per_page` (GitHub
resolves duplicates left-to-right on some paths). Low direct harm, but it is
uncontrolled parameter smuggling and it amplifies
[07.rate-limit-exhaustion.md](07.rate-limit-exhaustion.md).

### 3c. Ordinary breakage

A search for `C++`, `a b`, or anything containing `#`, `%`, or `+` produces a
wrong or truncated query. `#` truncates the URL entirely at the fragment. This
is a *functional* bug visitors will hit without trying.

## How to fix

Encode every interpolated value, and prefer `URL` + `URLSearchParams` over
string templates so encoding is not optional:

```ts
const url = new URL(`https://api.github.com/users/${encodeURIComponent(username)}/repos`);
url.searchParams.set("per_page", String(perPage));
url.searchParams.set("page", String(page));
const response = await fetch(url, { headers });
```

`encodeURIComponent` turns `/` into `%2F`, which GitHub treats as a literal
character inside one path segment — the traversal collapses.

Add the `isValidLogin` gate from
[02.graphql-query-injection.md](02.graphql-query-injection.md) at the route
boundary so malformed logins never reach a request at all. Validate `repoName`
with the equivalent GitHub repo-name grammar (`^[A-Za-z0-9_.-]{1,100}$`).

Also sanity-check `page`, which is currently `parseInt(searchParams.get("page") || "1", 10)`
([`Repositories.tsx:9`](../../client/src/page/Repositories.tsx#L9),
[`DisplayRepoList.tsx:17`](../../client/src/components/DisplayRepoList.tsx#L17))
and yields `NaN` for `?page=abc` — that `NaN` propagates into the URL and into
`Pagination`'s arithmetic.

## Contradictions & trade-offs

- **`useFetchSearchUsers.ts` is dead code.** `Explorer` uses `useInfiniteUsers`;
  nothing imports `useFetchSearchUsers`. Fixing it is wasted effort — delete it
  instead (see
  [../suggestions/12.repo-hygiene-and-dead-code.md](../suggestions/12.repo-hygiene-and-dead-code.md)).
  Verify before deleting.
- **Encoding the search query changes what GitHub search receives.** Today a
  user typing `location:india followers:>100` accidentally works as a GitHub
  search qualifier because `:` and `>` pass through. `encodeURIComponent` keeps
  `:` intact but encodes `>` to `%3E` — still correct, since GitHub decodes it.
  Verify the qualifier syntax still behaves after the change; it is a nice
  hidden feature to keep.
- **Strict `repoName` validation conflicts with
  [`UserProfileRepos.tsx:47`](../../client/src/components/UserProfileRepos.tsx#L47)**,
  which navigates to `/user/${repo.full_name}` — i.e. it deliberately injects a
  `/` into what the router matches as two segments. That works today by
  coincidence of route shape. Make it explicit:
  `navigate(\`/user/${owner}/${name}\`)`.
