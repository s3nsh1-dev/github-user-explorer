## What is wrong

`localStorage` is **not a trust boundary you control**. It is writable by the
user, by any browser extension with host permissions, by any other script on
the origin, and by every past version of your own app. The code reads it as if
it were internal state.

### 6a. `staredProfiles` — parsed and rendered without validation

```ts
// client/src/context/StaredUserContextProvider.tsx:9-12
const initialList: string[] = JSON.parse(
  window.localStorage.getItem("staredProfiles") || "[]"
);
const [staredList, setStaredList] = useState<string[]>(initialList);
```

The `: string[]` annotation is an assertion, not a check — `JSON.parse` returns
`any`. Whatever is in storage flows straight into:

```tsx
// client/src/components/StaredRepositories.tsx:71-75
{staredList.map((user) => (
  <MenuItem key={user} onClick={() => handleClose(user)}>{user}</MenuItem>
))}
```

…and `handleClose` does `navigate(\`/user/${user}\`)`
([`StaredRepositories.tsx:26`](../../client/src/components/StaredRepositories.tsx#L26)).

So a stored value propagates into a **route param**, and from there into the
GraphQL documents of
[02.graphql-query-injection.md](02.graphql-query-injection.md) and the REST
URLs of [03.api-url-tampering.md](03.api-url-tampering.md). Storage is a second
injection source that survives page reloads and is invisible in the address bar.

React escapes the rendered text, so this is **not** stored XSS. The impact is
persistent injection into API requests plus the crash paths in
[05.unhandled-api-errors.md](05.unhandled-api-errors.md).

### 6b. `mode` — cast, not validated

```ts
// client/src/context/ModeContextProvider.tsx:6-7
const localStorageValue = localStorage.getItem("mode") as ModeType;
const [mode, setMode] = useState<ModeType>(localStorageValue || "light");
```

`as ModeType` claims `"light" | "dark"` for a value that is `string | null`.
Set `localStorage.mode = "purple"` and every
`mode === "dark" ? A : B` in the codebase silently takes the light branch,
while `mode === "light" ? X : Y` takes the *dark* branch — because the codebase
compares against both literals in different places
(e.g. [`PageButton.tsx:19-32`](../../client/src/components/PageButton.tsx#L19)
vs [`muiCustomTheme.ts:20`](../../client/src/theme/muiCustomTheme.ts#L20)).
Result: an incoherent half-dark theme with unreadable contrast. Low severity,
but it is a genuine "the type system said this was safe and it wasn't" defect.

### 6c. Side effects inside a state updater

```ts
// StaredUserContextProvider.tsx:14-20
setStaredList((prev) => {
  const updated = [...prev, value];
  window.localStorage.setItem("staredProfiles", JSON.stringify(updated));  // ← side effect
  return updated;
});
```

React requires updater functions to be pure; it may call them more than once
(it does, under `StrictMode`, which is enabled at
[`main.tsx:12`](../../client/src/main.tsx#L12)). The write happens to be
idempotent here, so no corruption is observable today — but it is unsafe by
construction and will break the moment the updater stops being idempotent.

Related: `checkStared` and `updateStaredList`
([lines 22-40](../../client/src/context/StaredUserContextProvider.tsx#L22))
read `initialList` — a fresh `localStorage` read on *every render* — rather
than the `staredList` state. It currently agrees with state only because the
write above is synchronous. See
[../suggestions/06.starred-users-state.md](../suggestions/06.starred-users-state.md).

## How to fix

Parse at the boundary with a validating reader, and write from an effect:

```ts
// client/src/helper/storage.ts
import { isValidLogin } from "./validateLogin";

const KEY = "staredProfiles";

export const readStarred = (): string[] => {
  try {
    const raw = JSON.parse(localStorage.getItem(KEY) ?? "[]");
    if (!Array.isArray(raw)) return [];
    return [...new Set(raw.filter((v): v is string => typeof v === "string" && isValidLogin(v)))];
  } catch {
    return [];
  }
};

export const writeStarred = (list: string[]) => {
  try { localStorage.setItem(KEY, JSON.stringify(list)); } catch { /* quota / private mode */ }
};

export const readMode = (): "light" | "dark" => {
  const v = localStorage.getItem("mode");
  if (v === "light" || v === "dark") return v;
  return window.matchMedia?.("(prefers-color-scheme: dark)").matches ? "dark" : "light";
};
```

Then in the provider:

```ts
const [staredList, setStaredList] = useState<string[]>(readStarred);  // lazy init
useEffect(() => { writeStarred(staredList); }, [staredList]);          // effect, not updater
```

Note `useState(readStarred)` — passing the *function* makes React call it once,
instead of re-reading storage on every render.

`localStorage.setItem` can throw (`QuotaExceededError`, and Safari private mode
historically), so the write is wrapped too.

## Contradictions & trade-offs

- **Filtering by `isValidLogin` on read silently deletes existing bookmarks**
  for anyone whose stored data does not match the grammar. That is intended, but
  it *is* data loss on first load after deploy. Acceptable for this app; worth
  knowing.
- **`readMode`'s `prefers-color-scheme` fallback changes the default theme** for
  first-time visitors from always-light to system-matched. Desirable, but it
  changes what a reviewer sees on first load — decide whether the portfolio
  screenshot should be light or dark and make sure the README image matches.
- **Moving the write into a `useEffect` conflicts with the current
  two-provider layout.** `StaredUserContextProvider` is mounted twice
  independently — once in [`UpperHomeUI.tsx:17`](../../client/src/components/UpperHomeUI.tsx#L17)
  and once in [`ProfileInfo.tsx:120`](../../client/src/page/ProfileInfo.tsx#L120).
  With an effect-based write, two live instances can overwrite each other's
  list. **Hoist the provider to `App.tsx` in the same change** — see
  [../suggestions/06.starred-users-state.md](../suggestions/06.starred-users-state.md).
