## What is wrong

Three outbound links in [`ShowSelectedRepo.tsx`](../../client/src/page/ShowSelectedRepo.tsx)
open a new tab without a `rel` attribute:

```tsx
// line 132-138 — Forks chip
<Chip label={`${forks_count} Forks`} component="a"
      href={`${html_url}/network/members`} target="_blank" clickable variant="outlined" />

// line 145-151 — Issues chip
<Chip label={`${open_issues_count} Issues`} component="a"
      href={`${html_url}/issues`} target="_blank" clickable variant="outlined" />

// line 169-178 — Visit on GitHub button
<Button variant="contained" color="primary" href={html_url} target="_blank" … >
```

The rest of the codebase gets this right — [`UserCards.tsx:57`](../../client/src/components/UserCards.tsx#L57),
[`OrganizationTopRepos.tsx:110`](../../client/src/components/OrganizationTopRepos.tsx#L110),
and [`ProfileInfo.tsx:91`](../../client/src/page/ProfileInfo.tsx#L91) all pass
`rel="noopener noreferrer"`. This file is the outlier, which makes it a
consistency bug as much as a security one.

## Why the severity is Low, honestly

Chromium 88+, Firefox 79+, and Safari 12.1+ apply `noopener` **implicitly** to
`target="_blank"`, so `window.opener` is already `null` in every current
browser. The residual risk is:

1. **`noreferrer` is still not implicit.** The full URL of your page — including
   the searched username in the path — is sent to GitHub in the `Referer`
   header. Here the destination *is* GitHub, so this leaks nothing meaningful.
   It matters if `href` ever becomes a user-controlled URL (see below).
2. **`href` is API-controlled.** `html_url` comes from the GitHub API response
   ([`ShowSelectedRepo.tsx:52`](../../client/src/page/ShowSelectedRepo.tsx#L52))
   and is never validated to be a `https://github.com/…` URL. Today GitHub
   always returns that, so it is safe. If the fetch is ever pointed elsewhere —
   which [03.api-url-tampering.md](03.api-url-tampering.md) shows an attacker
   can do — `html_url` becomes attacker-influenced and the missing `rel` starts
   to matter.
3. Legacy browsers and embedded webviews that lag the implicit-noopener change.

It costs one attribute to close permanently, and a reviewer scanning your code
will notice the inconsistency.

## How to fix

```tsx
<Chip
  label={`${forks_count} Forks`}
  component="a"
  href={`${html_url}/network/members`}
  target="_blank"
  rel="noopener noreferrer"
  clickable
  variant="outlined"
/>
```

Then stop relying on remembering it. Add a linted rule:

```js
// client/eslint.config.js — add to the plugins/rules block
import jsxA11y from "eslint-plugin-jsx-a11y";
// plugins: { "jsx-a11y": jsxA11y }
// rules:   { "react/jsx-no-target-blank": "error" }   // via eslint-plugin-react
```

`eslint-plugin-react`'s `jsx-no-target-blank` catches this automatically,
including MUI's `component="a"` form when configured with
`linkComponents: [{ name: "Chip", linkAttribute: "href" }, { name: "Button", linkAttribute: "href" }]`.

A stronger option is a tiny `<ExternalLink>` wrapper that bakes in the `rel`,
so no call site can forget:

```tsx
// client/src/components/ExternalLink.tsx
export const externalLinkProps = { target: "_blank", rel: "noopener noreferrer" } as const;
```

…then spread `{...externalLinkProps}` everywhere. That is the cheapest fix
that also survives future components.

## Contradictions & trade-offs

- **Adding `eslint-plugin-react` will surface other warnings** on first run
  (the config today extends only `js.configs.recommended` and
  `tseslint.configs.recommended` — no React rules at all beyond hooks/refresh).
  Budget for a cleanup pass, or enable only `jsx-no-target-blank` and leave the
  rest off initially.
- **`noreferrer` suppresses referrer analytics.** If you ever want to see
  traffic you send to GitHub, `noreferrer` blocks it. Not a concern for this
  project; noted so the decision is deliberate.
- **No contradiction with the other findings** — this fix is independent and
  can ship on its own in five minutes. It is the best first commit if you want
  the report to start with a green checkmark.
