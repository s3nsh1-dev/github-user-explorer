## What is wrong

Every data-fetching hook reads the token from Vite's build-time environment and
attaches it to a request made **from the browser**:

```ts
// client/src/hooks/useFetchContributionInfo.ts:3
const TOKEN = import.meta.env.VITE_GITHUB_AUTHENTICATION_TOKEN;
...
headers: { Authorization: `Bearer ${TOKEN}` }
```

`import.meta.env.VITE_*` is **not** a runtime secret. Vite performs a literal
text substitution at build time, so the compiled `assets/index-*.js` contains
the raw token as a string. It is not encrypted, not obfuscated, and not
protected by the hosting platform's "environment variables" UI — that UI only
controls what gets baked in.

Anyone can retrieve it in about ten seconds:

```bash
curl -s https://<your-deployed-site>/ \
  | grep -oE 'assets/index-[A-Za-z0-9_-]+\.js' \
  | head -1 \
  | xargs -I{} curl -s https://<your-deployed-site>/{} \
  | grep -oE '(ghp|github_pat|gho|ghs)_[A-Za-z0-9_]+'
```

Or simply: open the site → DevTools → Network → any `api.github.com` request →
Request Headers → `Authorization: Bearer …`.

## Why it matters

The token is a **bearer credential tied to your GitHub account**. Whatever
scopes it carries, the finder inherits:

| Token scope | What an attacker gains |
|---|---|
| none / `public_repo` | 5,000 req/hr of *your* quota, attributable to you |
| `repo` | Read **and write** access to all your private repositories |
| `gist` | Create/modify gists under your identity |
| `delete_repo` | Repository deletion |
| `workflow` | Modify GitHub Actions workflows → CI compromise |

Even a zero-scope classic PAT is a real loss: rate-limit exhaustion (see
[07.rate-limit-exhaustion.md](07.rate-limit-exhaustion.md)), abuse traced back
to your account, and potential GitHub API ToS action against you for traffic
you did not send.

GitHub's secret-scanning partner program actively revokes tokens found in
public web content — so the practical outcome is often "the deployed portfolio
site silently stops working" with no obvious cause. That matches the
`5286e2c correcting deployed site` commit message ("deployed Site does not work
but loads correct data in console tab").

## Proof of impact (safe to run yourself)

```bash
# With the token lifted from your own bundle:
curl -H "Authorization: Bearer <TOKEN_FROM_BUNDLE>" https://api.github.com/user
# → returns YOUR account object, not the searched user's.
```

If that returns your login, the token is account-bound and this is confirmed
Critical.

## How to fix

**Immediately (do this first, before any code change):**

1. Revoke the token at <https://github.com/settings/tokens>. Assume it is
   already public.
2. Purge the value from every deployment platform (Vercel/Netlify/Render env
   vars) and from any local `.env`.
3. Check <https://github.com/settings/security-log> for unfamiliar activity.

**Then pick one of two architectures:**

### Option A — Drop the token entirely (fastest, zero infrastructure)

The REST endpoints this app uses (`/users/:u`, `/users/:u/repos`,
`/search/users`, `/repos/:o/:r`) all work **unauthenticated**. Delete every
`Authorization` header. Cost: 60 req/hr per IP instead of 5,000, and 10
searches/min instead of 30.

Casualty: the two GraphQL features. `api.github.com/graphql` **requires**
authentication, so `useFetchContributionInfo` (contribution calendar) and
`useFetchLoginType` / `useFetchOrganizationRepos` would have to be dropped or
reworked onto REST equivalents (`/users/:u` returns `type: "User" | "Organization"`,
which replaces `useFetchLoginType` outright).

### Option B — Backend proxy (correct, and the `server/` folder already exists)

Move all GitHub calls behind a small server that holds the token in a real
runtime secret. The client calls your API; your API calls GitHub. See
[../suggestions/01.backend-api-proxy.md](../suggestions/01.backend-api-proxy.md)
for the full design.

**Recommendation:** Option B. `server/` is already scaffolded (an empty
`package.json` stub), the repo is already laid out as a fullstack project, and
Option B is the only path that keeps the contribution-graph feature — which is
the most visually distinctive thing on the site.

## Contradictions & trade-offs

- **Contradicts Option A of this fix vs. the contribution-graph feature.** You
  cannot both remove the token and keep `ContributionChart`. Decide before
  refactoring; the whole hook layer changes shape either way.
- **Fixing this changes the severity of
  [02.graphql-query-injection.md](02.graphql-query-injection.md) *upward*, not
  downward.** Today the injection is low-value because the token is already
  public. Behind a proxy the token becomes secret again — and the injection
  becomes the new way to abuse it. **Fix 01 and 02 in the same change or you
  will have moved the vulnerability, not removed it.**
- **Option B introduces a cold-start / uptime dependency.** A free-tier proxy
  that sleeps means your portfolio demo takes 10s to load on first visit.
  Mitigate with a serverless function (Vercel/Netlify Functions) rather than a
  long-running Node process — no cold-start penalty worth worrying about, and
  no extra hosting bill.
- **Option B and [07.rate-limit-exhaustion.md](07.rate-limit-exhaustion.md)
  interact.** A proxy concentrates every visitor onto one token, so the shared
  5,000/hr limit is now a single shared pool. Add caching at the proxy at the
  same time.
