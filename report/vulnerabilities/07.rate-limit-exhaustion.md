## Before → After

Four separate problems, four separate fixes.

### 7a — the scroll observer

**Before** — the guard sat around the effect, not inside the callback:

```tsx
useEffect(() => {
  if (!hasNextPage || isFetchingNextPage) return;   // checked once per registration
  const observer = new IntersectionObserver((entries) => {
    if (entries[0].isIntersecting) fetchNextPage();  // fires on every scroll
  }, { threshold: 1.0 });
```

An already-live observer kept firing. Holding `End` walked pages as fast as the
network allowed — against GitHub's tightest limit (10/min unauthenticated,
30 authenticated). `threshold: 1.0` was a second bug: on a short viewport the
sentinel could never be *fully* visible, so pagination silently stopped.

**After:**

```tsx
const observer = new IntersectionObserver(
  ([entry]) => {
    if (entry.isIntersecting && hasNextPage && !isFetchingNextPage) fetchNextPage();
  },
  { root: null, rootMargin: "200px", threshold: 0 }
);
```

### 7b/7c — error typing and retry policy

**Before:** `if (!res.ok) throw new Error("Failed to fetch users")` — a 403 rate
limit was indistinguishable from anything else, and `new QueryClient()` used the
library default of **3 retries with backoff**. Each rate-limited request became
four, driving further past the limit.

**After:**

```ts
// main.tsx
retry: (failureCount, error) => {
  if (error instanceof RateLimitError) return false;  // retrying makes it worse
  if (error instanceof NotFoundError) return false;   // a 404 will not become a 200
  return failureCount < 1;
},
```

`RateLimitError` carries `resetAt`, read from `x-ratelimit-reset` — and the
proxy forwards GitHub's `x-ratelimit-*` headers verbatim precisely so this still
works across the hop.

### 7d — caching

| | Before | After |
|---|---|---|
| `staleTime` | 5 min in 6 hooks, **commented out** in `useFetchReposPerPage` | one default in `main.tsx` |
| `refetchOnWindowFocus` | library default (on) | off |
| `/users/:login` | fetched **twice** per profile, under two keys | once (P10 deleted the duplicate hook) |
| Paging | spinner flash between pages | `keepPreviousData` |
| Server-side | n/a | `s-maxage=300` — CDN answers repeats |

### Why the proxy made caching mandatory rather than optional

Before, each visitor had their own rate limit. Now every visitor shares one
token, so the 5,000/hr ceiling is a **single pool**. The `Cache-Control:
public, max-age=300, s-maxage=300` on every successful proxy response is what
keeps one enthusiastic scroller from taking the demo down for everyone. That
header shipped in the same change as the proxy, not later.

## What is wrong

### 7a. Nothing throttles or debounces request generation

The infinite-scroll loop fires whenever the sentinel intersects:

```tsx
// client/src/page/Explorer.tsx:45-67
const observer = new IntersectionObserver((entries) => {
  if (entries[0].isIntersecting) fetchNextPage();
}, { threshold: 1.0 });
```

`fetchNextPage` is not rate-limited, and the guard
`if (!hasNextPage || isFetchingNextPage) return;` runs when the *effect*
re-registers, not per-callback-invocation. A user holding `End`, or a scripted
`window.scrollTo` loop, walks through pages as fast as the network allows.

GitHub's search endpoint is the tightest one in the API:

| Endpoint | Unauthenticated | Authenticated |
|---|---|---|
| `/search/users` | **10 req/min** | **30 req/min** |
| Core REST | 60 req/hr | 5,000 req/hr |
| GraphQL | n/a (auth required) | 5,000 points/hr |

30 requests/minute is roughly 30 seconds of enthusiastic scrolling.

`guide.txt` lists *"Debounce user input for better UX (before calling navigate
or search)"* as a planned task. It was never done — the search still navigates
directly on submit ([`LowerHomeUI.tsx:33`](../../client/src/components/LowerHomeUI.tsx#L33)).
Submit-only search is much better than search-on-keystroke, so the current risk
is concentrated in the scroll path, not the input.

### 7b. HTTP 403 rate-limit responses are indistinguishable from real errors

Every hook collapses all failures into one message:

```ts
// client/src/hooks/useInfiniteUsers.ts:29
if (!res.ok) throw new Error("Failed to fetch users");
```

GitHub returns **403** (or 429) with `X-RateLimit-Remaining: 0` and an
`X-RateLimit-Reset` epoch header. None of that is read. The visitor sees
"Failed to fetch users" and assumes the site is broken. You see the same and
cannot tell rate limiting from a revoked token.

### 7c. React Query's default retry amplifies the problem

`new QueryClient()` ([`main.tsx:9`](../../client/src/main.tsx#L9)) uses the
library default of **3 retries with exponential backoff**. So each rate-limited
request becomes four requests, driving you further past the limit — a
self-reinforcing failure once the ceiling is hit.

### 7d. Caching is inconsistent, so identical data is refetched

`useFetchReposPerPage` has its `staleTime` **commented out**
([lines 34-35](../../client/src/hooks/useFetchReposPerPage.ts#L34)), so every
pagination click refetches, while its sibling hooks cache for 5 minutes. The
repositories page is exactly the screen a visitor clicks through fastest.

Additionally, `useFetchRepositories` and `useFetchUserData` fetch **the same
URL** (`/users/${username}`) under two different query keys
(`["public_repos", username]` vs `["userProfile", username]`) — every profile
visit costs two identical network requests where one would do.

## Combined impact

With the token public ([01](01.exposed-github-token.md)), an attacker does not
need your UI at all — they take the token and exhaust 5,000 req/hr directly,
and every visitor sees a broken site until the hour rolls over. Behind a proxy
([../suggestions/01.backend-api-proxy.md](../suggestions/01.backend-api-proxy.md)),
**all traffic funnels through one token**, so this stops being theoretical: one
bored visitor can take the demo down for everyone.

## How to fix

**1. Read the rate-limit headers and raise a typed error:**

```ts
// client/src/helper/githubFetch.ts
export class RateLimitError extends Error {
  constructor(public resetAt: Date) {
    super(`GitHub rate limit reached. Try again after ${resetAt.toLocaleTimeString()}.`);
  }
}

export async function githubFetch(url: string | URL, init?: RequestInit) {
  const res = await fetch(url, init);
  if (res.status === 403 || res.status === 429) {
    if (res.headers.get("x-ratelimit-remaining") === "0") {
      const reset = Number(res.headers.get("x-ratelimit-reset") ?? 0) * 1000;
      throw new RateLimitError(new Date(reset));
    }
  }
  if (!res.ok) throw new Error(`GitHub API error ${res.status}`);
  return res.json();
}
```

**2. Never retry a rate-limit failure:**

```ts
// main.tsx
const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 5 * 60_000,
      gcTime: 30 * 60_000,
      refetchOnWindowFocus: false,
      retry: (failureCount, error) => !(error instanceof RateLimitError) && failureCount < 1,
    },
  },
});
```

**3. Guard the observer inside the callback, not just the effect:**

```tsx
const observer = new IntersectionObserver(([entry]) => {
  if (entry.isIntersecting && hasNextPage && !isFetchingNextPage) fetchNextPage();
}, { rootMargin: "200px", threshold: 0 });
```

`threshold: 1.0` also means the sentinel must be *fully* visible — on a short
viewport with a tall sentinel that can never happen and pagination silently
stops. `threshold: 0` + `rootMargin` is both safer and smoother.

**4. Deduplicate `/users/:u`.** Delete `useFetchRepositories` and have
`Repositories.tsx` read `public_repos` from `useFetchUserData` under the shared
`["userProfile", username]` key. Halves the requests on the busiest screen.

**5. Restore `staleTime` in `useFetchReposPerPage`** and add
`placeholderData: keepPreviousData` so paging does not flash a spinner.

**6. Show a real rate-limit UI** — "GitHub rate limit reached, resets at
14:32" with a countdown — instead of "Failed to fetch users".

## Contradictions & trade-offs

- **Deleting `useFetchRepositories` conflicts with `Repositories.tsx`'s current
  independence from `ProfileInfo`.** Both live under `/user/:username`, split by
  `?tab=` in [`LinkWrapper.tsx`](../../client/src/page/LinkWrapper.tsx), so
  sharing one query key is safe — but only because React Query dedupes by key.
  Confirm the key is byte-identical in both call sites.
- **`refetchOnWindowFocus: false` conflicts with "always fresh" expectations.**
  For a GitHub browser this is right (profiles change slowly); if you later add
  a "live" feature, you will want it back per-query, not globally.
- **Raising `staleTime` fights the demo experience.** A reviewer who stars a
  profile then reloads expects to see it. Starred state is `localStorage`, not
  React Query, so it is unaffected — but be aware the two caches have different
  lifetimes.
- **Fix 3 (observer guard) subtly changes the "end of results" UI**, which is
  currently rendered twice and once unreachably
  ([`Explorer.tsx:110-120`](../../client/src/page/Explorer.tsx#L110)) — the
  inner `{!hasNextPage && …}` sits inside `{hasNextPage && …}` and can never
  render. Clean both up together; see
  [../suggestions/12.repo-hygiene-and-dead-code.md](../suggestions/12.repo-hygiene-and-dead-code.md).
