## Before → After

**Before** — six render paths printed an error value straight into a bare
`<div>`:

```tsx
if (error)     return <div>Error Message: {error.message}</div>;   // Explorer
if (userError) return <div>Error: {userError.message}</div>;       // ProfileInfo
Error loading repositories: {String(error)}                        // OrganizationTopRepos
```

The leaked strings were internal implementation naming — including the typo
`"Response for LongType was not ok"`, which tells a reader the code was never
reviewed. Six unstyled divs in an otherwise fully themed app.

**After** — one component classifies, and the detail never reaches the page:

```tsx
// client/src/components/ErrorState.tsx
const describe = (error: unknown) => {
  if (error instanceof RateLimitError)
    return { title: "GitHub rate limit reached",
             body: `Try again after ${error.resetAt.toLocaleTimeString()}.` };
  if (error instanceof NotFoundError)
    return { title: "Not found", body: "That GitHub user or repository doesn't exist." };
  return { title: "Something went wrong", body: "Couldn't load data from GitHub. Please try again." };
};

if (import.meta.env.DEV) console.error(error);   // detail stays in the console
```

### Previous vs current structure

| | Before | After |
|---|---|---|
| What the user sees | raw internal string | classified, actionable message |
| Styling | bare `<div>` ×6 | themed MUI `<Alert>`, dark mode included |
| Recovery | none — a dead end | `Retry` button wired to `refetch` |
| Where detail goes | the page | `console.error`, dev builds only |
| Proxy errors | n/a | fixed codes (`not_found`, `rate_limited`, …), never GitHub's text |

### The two-layer rule this resolved

Finding [05](05.unhandled-api-errors.md) says *throw the detailed message*.
This one says *don't show it*. Both are right, at different layers:

- **Throw** detail, so it reaches the console and React Query devtools.
- **Render** a classified generic message, so nothing internal reaches the page.

The same rule holds at the proxy: `netlify/functions/_shared/github.mts` maps
upstream failures onto a fixed `ProxyError` union rather than forwarding
GitHub's body — an upstream error can name the token's scopes or its owner.

### Why this got more important after the proxy, not less

Pre-proxy the token was public anyway, so leaking implementation detail cost
little. Once the credential became a real secret, error text became a
reconnaissance channel pointed at it. The generic-message rule landed in the
same session as the proxy.

## What is wrong

Six render paths print an error value straight into the DOM:

```tsx
// client/src/page/Explorer.tsx:75
if (error) return <div>Error Message: {error.message}</div>;

// client/src/page/ProfileInfo.tsx:52
if (userError) return <div>Error: {userError.message}</div>;

// client/src/page/ShowSelectedRepo.tsx:42
if (error) return <div>Error: {error.message}</div>;

// client/src/components/DisplayRepoList.tsx:37
if (reposError) return <div>Error: {reposError.message}</div>;

// client/src/components/OrganizationTopRepos.tsx:28
Error loading repositories: {String(error)}
```

`{String(error)}` in `OrganizationTopRepos` is the worst of these — for a
non-`Error` value it can serialise an object; for an `Error` it prints
`"Error: <message>"` with no stack, which is fine, but the shape is
unpredictable because the hook types `error` as `Error | unknown`
([`common.types.ts:133`](../../client/src/constants/common.types.ts#L133)).

## What actually leaks

Today the thrown messages are all hardcoded strings from the hooks
("Failed to fetch user repositories", "Response for LongType was not ok"), so
the current leak is essentially **internal implementation naming** — including
the typo `"LongType"`, which tells a reader the code was not reviewed.

The real risk is what happens after the *other* fixes land:

- [05.unhandled-api-errors.md](05.unhandled-api-errors.md) recommends rethrowing
  `json.errors[0].message` from GraphQL. GitHub's GraphQL errors can include
  the **offending query fragment**, which — combined with
  [02.graphql-query-injection.md](02.graphql-query-injection.md) — gives an
  attacker a free oracle for probing the injected document. That turns a blind
  injection into a visible one.
- A backend proxy ([../suggestions/01.backend-api-proxy.md](../suggestions/01.backend-api-proxy.md))
  that forwards upstream error bodies verbatim can leak header names, internal
  hostnames, or the token's rate-limit identity.

So this is Low **now** and becomes meaningful **exactly when you fix the higher
findings**. It is listed so the fix for 05 does not open it.

## Also: these are inconsistent and ugly

Five different unstyled `<div>`s in an otherwise fully MUI-themed app. On a
portfolio site, an error state that drops out of the design system is the kind
of detail a reviewer notices.

## How to fix

Classify errors once, render a safe message, log the detail:

```tsx
// client/src/components/ErrorState.tsx
import { Alert, AlertTitle, Button } from "@mui/material";
import { RateLimitError } from "../helper/githubFetch";

const userMessage = (error: unknown): { title: string; body: string } => {
  if (error instanceof RateLimitError)
    return { title: "GitHub rate limit reached", body: `Try again after ${error.resetAt.toLocaleTimeString()}.` };
  if (error instanceof NotFoundError)
    return { title: "Not found", body: "That GitHub user or repository doesn't exist." };
  return { title: "Something went wrong", body: "Couldn't load data from GitHub. Please try again." };
};

export const ErrorState = ({ error, onRetry }: { error: unknown; onRetry?: () => void }) => {
  if (import.meta.env.DEV) console.error(error);   // detail stays in the console, in dev
  const { title, body } = userMessage(error);
  return (
    <Alert severity="error" action={onRetry && <Button onClick={onRetry}>Retry</Button>}>
      <AlertTitle>{title}</AlertTitle>
      {body}
    </Alert>
  );
};
```

Then every call site becomes `if (error) return <ErrorState error={error} onRetry={refetch} />;`.

Three benefits at once: nothing internal is printed, the UI stays inside the
theme, and the visitor gets a `Retry` button instead of a dead end.

## Contradictions & trade-offs

- **Directly contradicts a naive reading of
  [05.unhandled-api-errors.md](05.unhandled-api-errors.md).** That finding says
  "throw `json.errors[0].message`"; this one says "don't show it". Both are
  right: **throw** the detailed message so it reaches logs and React Query
  devtools, **render** the classified generic message. Keep the two layers
  separate.
- **Hiding detail makes debugging your own deploy harder.** The
  `import.meta.env.DEV` console log covers local work, but production
  diagnosis needs something — either keep detail behind a `?debug=1` flag or
  accept that you will reproduce locally.
- **`ErrorState` needs `refetch` from each hook.** Several hooks currently
  destructure and discard it (`useFetchUserData`, `useFetchReposPerPage`,
  `useShowIndividualRepo` return only `data/isLoading/error`). Returning the
  whole query result — as `useFetchContributionInfo` and `useFetchLoginType`
  already do — makes the hook layer consistent; see
  [../suggestions/04.api-response-type-safety.md](../suggestions/04.api-response-type-safety.md).
