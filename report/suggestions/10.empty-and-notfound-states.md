## 10a. The 404 page

```tsx
// client/src/page/NotFound.tsx
const NotFound = () => <div>Not Found</div>;
```

Three words, unstyled, outside the theme, on a site that otherwise has a custom
dark mode and an animated theme switch. There is even a design mockup for this
screen sitting unused in the repo —
[`docs/design/userNotFound-design.png`](../../docs/design/userNotFound-design.png).

Make it a real page: themed, with the site's monospace voice, a search box, and
a link home.

```tsx
const NotFound = ({ title = "404", message = "That page doesn't exist." }) => (
  <Box sx={{ minHeight: "70vh", display: "grid", placeItems: "center", textAlign: "center", gap: 2 }}>
    <Typography fontFamily="monospace" fontSize={64}>{title}</Typography>
    <Typography color="text.secondary">{message}</Typography>
    <SearchBar />
    <Button component={RouterLink} to="/">Back to search</Button>
  </Box>
);
```

Parameterising it lets the same component serve "user not found", "repository
not found", and "page not found" — three states that currently produce either a
raw error string or a blank screen.

## 10b. `"demoUserName"` is fed to the API as a real username

Five call sites substitute a placeholder for a missing param:

```tsx
// ProfileInfo.tsx:46      username: username || "demoUserName"
// ProfileInfo.tsx:127     <ContributionChart username={username || "demoUserName"} />
// Repositories.tsx:10,18  useFetchRepositories(username || "demoUserName")
// DisplayRepoList.tsx:19  username: username || "demoUserName"
// ShowSelectedRepo.tsx:30-31  repoName: repoName || "demoRepo", username: username || "demoUserName"
```

These are not placeholders — they are **real requests to
`api.github.com/users/demoUserName`**, which 404s, which surfaces as "Failed to
fetch user profile", which (per
[03.loading-error-state-ordering.md](03.loading-error-state-ordering.md)) never
renders anyway.

The fallbacks exist only to satisfy TypeScript, because `useParams()` returns
`string | undefined`. The honest fix is to handle the `undefined` case:

```tsx
const { username } = useParams();
if (!username || !isValidLogin(username)) return <NotFound title="Invalid username" … />;
```

This pairs directly with the validation gate in
[`../vulnerabilities/02.graphql-query-injection.md`](../vulnerabilities/02.graphql-query-injection.md)
and [`../vulnerabilities/03.api-url-tampering.md`](../vulnerabilities/03.api-url-tampering.md)
— one guard, three findings closed.

## 10c. `Explorer` with no query searches for `"noQueryToSearch"`

```tsx
// Explorer.tsx:41
useInfiniteUsers(query || "noQueryToSearch");
```

Visiting `/explore` directly fires a real GitHub search for that literal string
and renders "Matching Results : 0" with an empty grid. Show a prompt instead:

```tsx
if (!query) return <EmptyState title="Search for a GitHub user" action={<SearchBar />} />;
```

## 10d. Zero-result search shows nothing

When a valid search returns `total_count: 0`, `Explorer` renders "Matching
Results : 0", an empty `<Box>`, and — because `hasNextPage` is false — the
celebratory *"🎉 You've reached the end of results!"*. Celebrating zero results
is a bad moment. Branch on `total_count === 0` and suggest checking the
spelling.

## 10e. Dead, unreachable end-of-results markup

```tsx
// Explorer.tsx:96-120
{hasNextPage && (
  <>
    <Box ref={loadRef} sx={style6}>{isFetchingNextPage && <CircularProgress />}</Box>
    {!hasNextPage && (                       // ← inside `hasNextPage &&`: never true
      <Box>🎉 You've reached the end of results!</Box>
    )}
  </>
)}

{!hasNextPage && (                            // ← the one that actually renders
  <Box sx={style5}>🎉 You've reached the end of results!</Box>
)}
```

The inner block is unreachable by construction. Delete it.

| State | Today | Should be |

| Organization with 0 repos | "🚫 No repositories found for this organization" | Fine — this one is already decent |
| Offline / network failure | Generic error string | "You appear to be offline" via `navigator.onLine` |

The starred-users dropdown is the most jarring: a first-time visitor lands on
the home page, sees "Stared User Profiles", clicks it, and gets an empty box.
That is the **first interactive element on the site**.

## 10g. Route ordering is fine — but make it readable

```tsx
// App.tsx:19-28
<Route path="*" element={<NotFound />} />
<Route path="/user/:username/:repoName" element={<ShowSelectedRepo />} />
```

The catch-all is declared **before** a more specific route. This works: React
Router v6+ ranks routes by specificity rather than declaration order, so
`/user/x/y` still matches `ShowSelectedRepo`. It is not a bug — but every
reader has to stop and verify that, so move `*` last anyway.

## Contradictions & trade-offs

- **Removing the `"demoUserName"` fallbacks requires the validation helper from
  [`../vulnerabilities/02`](../vulnerabilities/02.graphql-query-injection.md) to
  exist first**, otherwise you are just moving the `|| ""` around. Build
  `isValidLogin` before this.
- **A hard 404 on an invalid username is stricter than today's behaviour.** A
  username GitHub accepts but the regex rejects would become unreachable. The
  regex encodes GitHub's documented rules (alphanumeric, single internal
  hyphens, ≤39 chars) — verify against a few real edge cases before shipping.
- **`SearchBar` on the 404 page is a forward dependency on
  [05.search-ux-and-debounce.md](05.search-ux-and-debounce.md).** Build the
  shared component once; do not inline a second copy of the home-page form.
- **10d conflicts with the "🎉" tone.** Two different messages for
  "no more results" and "no results at all" — keep them clearly distinct or the
  emoji reads as sarcasm.
