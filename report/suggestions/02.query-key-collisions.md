# 02 · React Query Cache Keys Are Colliding and Inconsistent

| Field | Value |
|---|---|
| **Impact** | 🟠 High — one confirmed data-correctness bug, one latent |
| **Effort** | ~1 hour |
| **Portfolio value** | High — cache-key discipline is exactly what an interviewer probes when you list TanStack Query |

---

## 2a. Confirmed bug: repo detail ignores the owner

```ts
// client/src/hooks/useShowIndividualRepo.ts:17
queryKey: [repoName, "keyIsUnique"],
```

The key contains **`repoName` only**. `username` is used in the request URL but
not in the key. So two different owners with the same repo name share one cache
entry.

**Reproduce:**

1. Visit `/user/facebook/react` → correct data cached under `["react", "keyIsUnique"]`
2. Visit `/user/typescript-cheatsheets/react` within the 5-minute `staleTime`
3. **You are shown Facebook's React repo** — stars, description, license, all wrong

This is not theoretical; common names like `react`, `blog`, `portfolio`,
`dotfiles`, or `api` collide constantly. And the literal string
`"keyIsUnique"` in the key is a comment asserting the opposite of what the
code does.

**Fix:**

```ts
queryKey: ["repo", username, repoName],
```

## 2b. Latent bug: two different hooks share one key

```ts
// client/src/hooks/useFetchContributionInfo.ts:25
queryKey: ["contributionInfo", username],

// client/src/hooks/useFetchOrganizationRepos.ts:25   ← copy-paste, never renamed
queryKey: ["contributionInfo", username],
```

Two hooks returning **completely different response shapes** under one key.
It does not detonate today only because
[`ContributionChart.tsx:10-14`](../../client/src/components/ContributionChart.tsx#L10)
renders exactly one of them per login, and a login is either a User or an
Organization — never both.

That is a coincidence of the current control flow, not a guarantee. The moment
anything renders both (a comparison view, a prefetch, devtools poking a query),
one component reads `data.data.user…` from an organization payload and throws.
Rename it:

```ts
queryKey: ["organizationRepos", username],
```

## 2c. Duplicate request for identical data

`useFetchUserData` and `useFetchRepositories` fetch the **same URL**
(`https://api.github.com/users/${username}`) under different keys:

| Hook | Key | Used by |
|---|---|---|
| [`useFetchUserData.ts:11`](../../client/src/hooks/useFetchUserData.ts#L11) | `["userProfile", username]` | `ProfileInfo` |
| [`useFetchRepositories.ts:7`](../../client/src/hooks/useFetchRepositories.ts#L7) | `["public_repos", username]` | `Repositories` |

`useFetchRepositories` exists solely to read `public_repos` — a field already
present in the `userProfile` payload. Delete it and read from the shared key;
React Query then dedupes across both tabs of `/user/:username` for free.

## 2d. Inconsistent key ordering

```ts
["contributionInfo", username]   // noun first
[username, "loginType"]          // noun last  ← useFetchLoginType.ts:11
[repoName, "keyIsUnique"]        // noun last, and wrong
["userRepos", username, page]    // noun first
```

Not a bug, but it makes invalidation impossible to reason about.
`queryClient.invalidateQueries({ queryKey: ["userProfile", "torvalds"] })`
works; there is no equivalent prefix match for the `[username, ...]` forms.

## Recommended: centralise the keys

```ts
// client/src/constants/queryKeys.ts
export const qk = {
  userProfile:  (login: string) => ["userProfile", login] as const,
  userRepos:    (login: string, page: number) => ["userRepos", login, page] as const,
  repo:         (owner: string, name: string) => ["repo", owner, name] as const,
  searchUsers:  (q: string) => ["searchUsers", q] as const,
  ownerType:    (login: string) => ["ownerType", login] as const,
  contributions:(login: string) => ["contributions", login] as const,
  orgRepos:     (login: string) => ["orgRepos", login] as const,
} as const;
```

Every hook then uses `queryKey: qk.repo(username, repoName)`. Collisions become
impossible by construction, and `as const` gives TanStack Query v5 proper key
inference. This is a ten-minute refactor that removes a whole class of bug —
and it is a genuinely good thing to be able to point at.

## Contradictions & trade-offs

- **Deleting `useFetchRepositories` couples `Repositories` to the profile
  payload.** Fine while both are `/user/:username` tabs behind
  [`LinkWrapper`](../../client/src/page/LinkWrapper.tsx). If repositories ever
  becomes a standalone route, it still works — it just fetches the profile
  first. Note the cost is a full user object instead of one number.
- **Fixing 2a invalidates existing caches** — irrelevant here (memory-only, no
  persistence), but worth knowing if you later add `persistQueryClient`.
- **The `qk` refactor touches every hook**, so it collides with the URL-encoding
  fix ([`../vulnerabilities/03.api-url-tampering.md`](../vulnerabilities/03.api-url-tampering.md))
  and the proxy migration ([01.backend-api-proxy.md](01.backend-api-proxy.md)),
  which also touch every hook. **Do all three in one pass** rather than three
  conflicting refactors of the same files.
- **`useInfiniteUsers` currently keys on `["users", query]`** — the same prefix
  as the dead `useFetchSearchUsers`. Deleting that dead hook
  ([12.repo-hygiene-and-dead-code.md](12.repo-hygiene-and-dead-code.md)) removes
  the ambiguity; do it before renaming, or you will rename a file you were about
  to delete.
