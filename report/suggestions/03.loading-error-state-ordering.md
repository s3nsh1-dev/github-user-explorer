## Before → After

**Before** — the guards ran in an order that made two of them unreachable:

```tsx
if (!userData) return null;                                    // ← runs first
const userProfile = mapGitHubResponse(userData as GitHubApiUser);
if (userLoading) return <div>Loading...</div>;                 // ← never reached
if (userError)   return <div>Error: {userError.message}</div>; // ← never reached
```

While loading, `userData` is `undefined` → `null` returned → **no spinner**. On
failure `userData` is also `undefined` → **no error message, ever**. The app's
main page rendered a blank area under the navbar during every load and
permanently after any failure.

**After** — guards in the order the states actually occur:

```tsx
if (userLoading) return <ProfileSkeleton />;
if (userError)   return <ErrorState error={userError} onRetry={refetchUser} />;
if (!userData)   return <NotFound title="User not found" />;

const userProfile = mapGitHubResponse(userData);
```

### Previous vs current

| State | Before | After |
|---|---|---|
| Loading | blank area | `<ProfileSkeleton />` matching the real layout |
| Error | blank area, forever | `<ErrorState>` with a Retry button |
| No data | blank area | themed 404 |
| Invalid username | fetched `"demoUserName"` from the API | rejected before any request |
| `mapGitHubResponse` | ran **before** the error check | runs only on real data |

### The second bug in the same family

`Repositories.tsx` passed `data?.public_repos` — `number | undefined` — into a
prop declared `number`. TypeScript did not catch it because untyped `useQuery`
made `data` `any`, and `any` is assignable to `number`. At runtime:

```ts
Math.ceil(undefined / 8)  // NaN
// NaN <= 3 is false AND NaN > 3 is false → both branches skipped
```

No page numbers rendered, and the "last page" link pointed at `?page=NaN`. The
fix was an explicit loading branch plus `helper/paginate.ts` as pure, tested
functions — `pageWindow(1, NaN)` now returns `[]` and there is a test row
asserting it.

### The third: an animation that never ran

`LoadingSkeleton` set `animation: "pulse 1.5s infinite"` with **no
`@keyframes pulse` defined anywhere** — not in `index.css` (9 lines, none), not
in the theme. It had been a static grey grid the whole time. Replaced with MUI's
`<Skeleton>`, which animates for free and drops the hardcoded `#e0e0e0` that
looked wrong in dark mode.

## 3a. Confirmed bug: `ProfileInfo` shows nothing while loading and nothing on error

```tsx
// client/src/page/ProfileInfo.tsx:49-52
if (!userData) return null;                                     // ← runs first
const userProfile: GitHubUser = mapGitHubResponse(userData as GitHubApiUser);
if (userLoading) return <div>Loading...</div>;                  // ← unreachable
if (userError) return <div>Error: {userError.message}</div>;    // ← unreachable
```

While the request is in flight, `userData` is `undefined`, so the component
returns `null` and the **"Loading…" branch can never execute**. On failure,
`userData` is also `undefined` — so the **error message can never render
either**. The visitor gets a completely blank page under the navbar, with no
spinner and no explanation, for the entire duration of the request and forever
after a failure.

This is the profile page — the primary destination of the whole app.

It also means `mapGitHubResponse` runs on line 50 before the error check, so a
malformed payload throws there rather than being reported.

**Fix — guard in the order the states actually occur:**

```tsx
if (userLoading) return <ProfileSkeleton />;
if (userError)   return <ErrorState error={userError} />;
if (!userData)   return <NotFound />;

const userProfile = mapGitHubResponse(userData as GitHubApiUser);
```

## 3b. `Repositories` passes `undefined` where a `number` is declared

```tsx
// client/src/page/Repositories.tsx:11
const totalRepos = fullRepoCall.data?.public_repos;   // number | undefined
...
<Pagination page={pNum} username={…} totalRepos={totalRepos} />
```

`PaginationProps.totalRepos` is typed `number`
([`common.types.ts:88`](../../client/src/constants/common.types.ts#L88)), and
`DisplayRepoList`'s prop type says `number` too
([line 10](../../client/src/components/DisplayRepoList.tsx#L10)). **TypeScript
does not catch the mismatch** because `useQuery` is never given a generic, so
`fullRepoCall.data` is `any` — and `any` is assignable to `number`. The strict
config in [`tsconfig.app.json`](../../client/tsconfig.app.json) is doing nothing
here because the type information was lost at the fetch boundary.

The runtime consequence, in [`Pagination.tsx:15`](../../client/src/components/Pagination.tsx#L15):

```ts
const totalPages = Math.ceil(totalRepos / 8);   // Math.ceil(undefined / 8) → NaN
```

`NaN <= 3` is `false` and `NaN > 3` is `false`, so **both branches are skipped**
and `renderNumericButtons` stays `undefined`. During the first render pass the
pagination bar shows only arrows, no page numbers. The "last page" button links
to `?page=NaN`, and `disabled={page === totalPages}` is always `false` because
`NaN !== NaN`.

**Fix:** make the loading state explicit rather than papering over it —

```tsx
const { data, isLoading } = useFetchUserData({ username });
if (isLoading) return <RepoListSkeleton />;
const totalRepos = data?.public_repos ?? 0;
```

…and type the hook properly so the compiler catches the next one
([04.api-response-type-safety.md](04.api-response-type-safety.md)).

## 3c. Inconsistent loading UI across the app

Five different treatments for the same state:

| Location | Loading UI |
|---|---|
| [`Explorer.tsx:69-74`](../../client/src/page/Explorer.tsx#L69) | `<CircularProgress />` in a 40px box |
| [`DisplayRepoList.tsx:23-36`](../../client/src/components/DisplayRepoList.tsx#L23) | `<CircularProgress />` in an 80vh box |
| [`ShowSelectedRepo.tsx:34-41`](../../client/src/page/ShowSelectedRepo.tsx#L34) | MUI `<Skeleton />` |
| [`UserContributions.tsx:25`](../../client/src/components/UserContributions.tsx#L25) | Custom 52×7 grid skeleton |
| [`ProfileInfo.tsx:51`](../../client/src/page/ProfileInfo.tsx#L51) | Plain `<div>Loading...</div>` (unreachable) |

The custom `LoadingSkeleton` for the contribution grid is genuinely nice — it
mirrors the real layout. Extend that idea: skeletons that match the final
layout everywhere, so the page does not jump. Spinners in an 80vh container
guarantee a large layout shift when content arrives.

Also: `LoadingSkeleton` sets `animation: "pulse 1.5s infinite"`
([line 39](../../client/src/components/LoadingSkeleton.tsx#L39)) but no
`@keyframes pulse` is defined in [`index.css`](../../client/src/index.css) (9
lines, no keyframes) or in the MUI theme. **The animation never runs** — the
skeleton is a static grey grid. Either define the keyframes or use MUI's
`<Skeleton variant="rounded" />`, which animates for free.

## Contradictions & trade-offs

- **Fixing 3a changes what an empty/invalid username renders.** Today it falls
  back to `username || "demoUserName"` and quietly fetches a non-existent user;
  after the fix it renders `NotFound`. That is correct, but it depends on
  [10.empty-and-notfound-states.md](10.empty-and-notfound-states.md) landing —
  otherwise you replace a blank page with `<div>Not Found</div>`, which is
  barely better.
- **Skeletons conflict with `staleTime` tuning.** With a 5-minute `staleTime`
  and `placeholderData: keepPreviousData`, cached navigation shows no loading
  state at all — so an elaborate skeleton is only visible on cold loads. Build
  the skeletons, but do not over-invest in them.
- **3b's fix depends on
  [02.query-key-collisions.md](02.query-key-collisions.md)**, which deletes
  `useFetchRepositories` in favour of `useFetchUserData`. Do that first, then
  this becomes a two-line change instead of a restructure.
