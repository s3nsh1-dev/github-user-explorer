## Before → After

**Before** — the type system stopped at `fetch`:

```ts
const { data: userData } = useQuery({
  queryKey: ["userProfile", username],
  queryFn: async () => {
    const response = await fetch(...);
    return await response.json();   // Promise<any>
  },
});
```

`Response.json()` returns `Promise<any>`, and 7 of 8 hooks passed no generic. So
**every piece of API data in the app was `any`**, and `strict: true` saw none of
it. The `NaN` bug in [03](03.loading-error-state-ordering.md) compiled cleanly
for exactly this reason.

**After** — schemas, with the types derived from them:

```ts
// client/src/constants/schemas.ts
export const GitHubApiUserSchema = z.object({
  login: z.string(),
  hireable: z.boolean().nullish(),          // GitHub returns null for most accounts
  type: z.enum(["User", "Organization"]),
  // …
});
export type GitHubApiUser = z.infer<typeof GitHubApiUserSchema>;   // ← derived
```

```ts
// client/src/helper/githubFetch.ts
function validate<T>(json: unknown, schema: z.ZodType<T>): T {
  const parsed = schema.safeParse(json);
  if (!parsed.success) {
    if (import.meta.env.DEV) console.error("Schema mismatch:", parsed.error.issues);
    throw new GitHubError("Unexpected response shape from GitHub");
  }
  return parsed.data;
}
```

### Previous vs current

| | Before | After |
|---|---|---|
| Payload type | `any` | `z.infer<typeof Schema>` |
| Where types come from | hand-written interfaces | derived from the schema |
| Runtime check | none | `.safeParse` at the boundary |
| `hireable` | `boolean` (wrong — API sends `null`) | `boolean \| null` |
| `error` field | `Error \| unknown` — collapses to `unknown` | `GitHubError` |
| Search results | typed `GitHubUser[]` (far too wide) | the actual narrower shape |
| Casts at call sites | `userData as GitHubApiUser` | none |

### Why derived types rather than types *plus* schemas

Writing both means two sources of truth that drift. `z.infer` makes the type a
consequence of the check, so a schema change is a compile error at every call
site — which is the property that was missing in the first place.

### Why `.safeParse`, always

A schema gap is a handled condition, not a crash: GitHub adds a field, the proxy
hiccups, an account has an unusual shape. `.parse` throws, which lands back at
the white screen [vulnerabilities/05](../vulnerabilities/05.unhandled-api-errors.md)
is about. `.safeParse` degrades into an `<ErrorState>`, with the issue detail in
the dev console only.

`.nullish()` is used liberally on optional profile fields — `blog`, `company`,
`email`, `twitter_username` are `null` *or absent* depending on the account, and
a too-strict schema rejects users GitHub returns happily.

## The problem in one line

```ts
// client/src/hooks/useFetchUserData.ts:12-18
const { data: userData } = useQuery({
  queryKey: ["userProfile", username],
  queryFn: async () => {
    const response = await fetch(...);
    return await response.json();   // ← Promise<any>
  },
});
```

`Response.json()` returns `Promise<any>`. No generic is passed to `useQuery`,
so `userData` is `any`. **`any` disables every check downstream**, and this
repeats in seven of the eight hooks — only
[`useInfiniteUsers`](../../client/src/hooks/useInfiniteUsers.ts) passes a type
argument.

[`tsconfig.app.json`](../../client/tsconfig.app.json) enables `strict`,
`noUnusedLocals`, `noUnusedParameters`, `noFallthroughCasesInSwitch` — a good
config that cannot see any of the data the app actually renders.

## What it already costs you

**1. The `undefined`/`number` bug in
[03.loading-error-state-ordering.md](03.loading-error-state-ordering.md#3b-repositories-passes-undefined-where-a-number-is-declared)
compiles cleanly.** `fullRepoCall.data?.public_repos` is `any`, assignable to
the declared `number`, so `NaN` reaches `Math.ceil` with the compiler's
blessing.

**2. The `as` casts are unchecked assertions:**

```tsx
// ProfileInfo.tsx:50
const userProfile: GitHubUser = mapGitHubResponse(userData as GitHubApiUser);
```

`userData` is `any`; `as GitHubApiUser` asserts a shape nobody verified.

**3. `Error | unknown` collapses to `unknown`:**

```ts
// common.types.ts:133 and :159
error: Error | unknown;
```

A union with `unknown` *is* `unknown`. So `OrganizationTopRepos` cannot call
`error.message` and falls back to `String(error)`
([line 28](../../client/src/components/OrganizationTopRepos.tsx#L28)) — the
type is actively causing worse code.

**4. `data.data.user.contributionsCollection.contributionCalendar.weeks`**
([`UserContributions.tsx:31-32`](../../client/src/components/UserContributions.tsx#L31))
type-checks against `ContributionCalendarResponse`, which models only the
success case. The `errors` variant is unrepresented, so the crash in
[`../vulnerabilities/05.unhandled-api-errors.md`](../vulnerabilities/05.unhandled-api-errors.md)
is invisible to the compiler.

**5. Duplicated `Week` / `ContributionDay` types.** Declared inline at
[`UserContributions.tsx:7-15`](../../client/src/components/UserContributions.tsx#L7)
*and* structurally inside `ContributionCalendarResponse`
([`common.types.ts:137-154`](../../client/src/constants/common.types.ts#L137)).
Two definitions of one thing drift.

## Recommended approach

### Minimum: generics + a discriminated GraphQL envelope

```ts
// client/src/constants/graphql.types.ts
export type GraphQLResponse<T> =
  | { data: T; errors?: undefined }
  | { data: null; errors: Array<{ message: string }> };
```

```ts
const result = useQuery<GitHubApiUser, Error>({
  queryKey: qk.userProfile(username),
  queryFn: () => githubFetch<GitHubApiUser>(url),
});
```

with

```ts
// client/src/helper/githubFetch.ts
export async function githubFetch<T>(url: string | URL, init?: RequestInit): Promise<T> {
  const res = await fetch(url, init);
  if (!res.ok) throw new GitHubError(res.status);
  return res.json() as Promise<T>;
}
```

This is still an assertion at the last line, but it is **one** assertion in one
audited place instead of seven scattered `any`s, and everything downstream is
genuinely typed.

### Better: validate at runtime with Zod

```ts
import { z } from "zod";

export const GitHubApiUserSchema = z.object({
  login: z.string(),
  node_id: z.string(),
  avatar_url: z.string().url(),
  name: z.string().nullable(),
  bio: z.string().nullable(),
  public_repos: z.number(),
  followers: z.number(),
  following: z.number(),
  created_at: z.string(),
  updated_at: z.string(),
  type: z.enum(["User", "Organization"]),
  hireable: z.boolean().nullable(),
  twitter_username: z.string().nullable(),
  // …
});
export type GitHubApiUser = z.infer<typeof GitHubApiUserSchema>;
```

```ts
queryFn: async () => GitHubApiUserSchema.parse(await githubFetch(url)),
```

Now the type is *derived from* the check, so they cannot disagree — and a
GitHub API change produces a clear parse error instead of `undefined is not an
object` three components away. ~14 kB gzipped, and it doubles as the validation
layer for [`../vulnerabilities/06.untrusted-localstorage.md`](../vulnerabilities/06.untrusted-localstorage.md).

**Recommendation:** generics now (an hour, zero dependencies), Zod when you next
touch the hook layer.

## Contradictions & trade-offs

- **Real types will surface errors the `any` was hiding.** Expect the first
  `tsc -b` after this change to fail in several files — that is the point, but
  budget for it rather than being surprised mid-refactor.
- **Zod adds a runtime dependency to a client that currently ships only React +
  MUI + Query.** If the bundle-size work in
  [07.asset-and-bundle-weight.md](07.asset-and-bundle-weight.md) matters to you,
  note that 14 kB gzipped is roughly 3% of the current JS — trivial next to the
  1.4 MB favicon, but a real trade.
- **Strict validation will reject users GitHub returns happily.** Optional
  fields (`blog`, `company`, `email`, `twitter_username`) are `null` or absent
  depending on the account. Use `.nullish()` liberally, and prefer
  `.safeParse()` over `.parse()` so a schema gap degrades instead of crashing.
- **Touches the same eight files as
  [01.backend-api-proxy.md](01.backend-api-proxy.md),
  [02.query-key-collisions.md](02.query-key-collisions.md), and
  [`../vulnerabilities/03`](../vulnerabilities/03.api-url-tampering.md).**
  Sequence them as one hook-layer rewrite: URLs → keys → types → proxy.
