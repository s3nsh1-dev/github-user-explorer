🚫 **MSW, Playwright and component tests were deliberately not added.** The

dependencies were installed — `vitest` and `jsdom` — because without component
tests, `@testing-library/react` and `jest-dom` have nothing to do.

⚠️ **What the test suite cannot cover, and what covers it instead:** everything
in this app renders through MUI, so there is no raw `<button>` or `<a>` for a
static check to reason about. Accessible names, focus visibility and colour
contrast were verified in S8 by driving the *rendered* DOM in headless Chrome.
Those checks are not committed as tests, and a lint rule cannot replace them —
see the P29 note in [09.accessibility.md](09.accessibility.md).

⚠️ The verification gate has **five** steps now — lint, `tsc -b --noEmit`,
`npm run test:run`, build, and `npm run typecheck:functions` whenever
`netlify/` is touched. **CI runs all five.**

## What to test, in priority order

### 1. Pure functions — cheapest, highest signal

```ts
// client/src/helper/simplifyGitHubResponse.test.ts
import { describe, it, expect } from "vitest";
import { mapGitHubResponse } from "./simplifyGitHubResponse";

describe("mapGitHubResponse", () => {
  it("substitutes placeholders for null fields", () => {
    const result = mapGitHubResponse({ login: "octocat", name: null, bio: null, /* … */ } as GitHubApiUser);
    expect(result.name).toBe("🚫 Not Provided");
    expect(result.bio).toBe("🚫 Not Provided");
  });

  it("maps hireable to a status string", () => {
    expect(mapGitHubResponse({ hireable: true,  /* … */ }).hirable).toBe("📨 Actively Applying");
    expect(mapGitHubResponse({ hireable: null,  /* … */ }).hirable).toBe("🧑‍💻 Busy Learning");
  });
});
```

That second case documents a real behaviour: `hireable: null` (the value GitHub
returns for most accounts) and `hireable: false` are both rendered as
"Busy Learning". Intentional, but currently undocumented — and the type says
`boolean`, not `boolean | null`
([04.api-response-type-safety.md](04.api-response-type-safety.md)).

Also test `isValidLogin` (once it exists) with the injection payloads from
[`../vulnerabilities/02`](../vulnerabilities/02.graphql-query-injection.md) —
a security regression test that is genuinely worth pointing at:

```ts
it("rejects GraphQL injection payloads", () => {
  expect(isValidLogin('a") { __typename } viewer { login }')).toBe(false);
  expect(isValidLogin("x/../../orgs/github")).toBe(false);
});
```

## CI

```yaml
# .github/workflows/ci.yml
name: CI
on:
  push: { branches: [main] }
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: client } }
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm, cache-dependency-path: client/package-lock.json }
      - run: npm ci
      - run: npm run lint
      - run: npx tsc -b --noEmit
      - run: npm test -- --run
      - run: npm run build
      - run: npm audit --audit-level=high
        continue-on-error: true
```

Note `npx tsc -b --noEmit` as a separate step: `npm run build` already runs
`tsc -b`, but a standalone type-check step makes a type error obvious in the
job list instead of buried in a build log.

## Contradictions & trade-offs

- **Writing tests against the current code locks in its bugs.** If you test
  `Pagination` as it stands, you encode `NaN` behaviour as expected. **Fix
  [03.loading-error-state-ordering.md](03.loading-error-state-ordering.md) and
  [02.query-key-collisions.md](02.query-key-collisions.md) first**, then write
  tests that assert the corrected behaviour.
- **Extracting `pageWindow` from `Pagination.tsx` changes a component you may
  also be restyling** for [09.accessibility.md](09.accessibility.md). Extract
  the logic first (pure refactor, no visual change), then do the a11y pass on
  the thinner component.
- **MSW plus Playwright is a lot of tooling for a project this size.** If you
  only have an afternoon: Vitest + the two pure-function suites + the CI
  workflow. That is 80% of the signal for 20% of the effort, and the CI badge
  in the README is what a reviewer actually sees.
- **`npm audit` will likely fail on transitive dev dependencies** you cannot
  fix. Hence `continue-on-error: true` — a red X on every PR for an unfixable
  advisory trains you to ignore CI.
- **CI requires the root/workspace question from
  [`../vulnerabilities/10`](../vulnerabilities/10.secret-and-dependency-hygiene.md)
  to be settled.** The workflow above assumes `working-directory: client`; if
  you convert to npm workspaces, the paths change.
