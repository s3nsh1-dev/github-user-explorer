## 13a. No SPA fallback configuration exists in the repo

The repo contains **no** `vercel.json`, `netlify.toml`, `public/_redirects`,
`public/_headers`, or `staticwebapp.config.json`. Whatever rewrite rule the live
site has (if any) lives only in a hosting dashboard — undocumented, unversioned,
and lost if the project is redeployed.

This matters because every route except `/` is client-side only:

```tsx
// client/src/App.tsx:19-28
<Route path="/explore" … />
<Route path="/user/:username" … />
<Route path="/user/:username/:repoName" … />
```

A static host asked for `/user/torvalds` looks for a file at that path, does not
find one, and returns 404 — the React app never boots. The symptom is
distinctive: **the site works when you navigate by clicking, and 404s when you
refresh or paste a link**.

That is precisely the class of problem behind commit `5286e2c`
("deployed Site does not work but loads correct data in console tab"). Whether
or not it is currently configured, put it in the repo:

```json
// vercel.json
{ "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }] }
```

```
# client/public/_redirects   (Netlify)
/*  /index.html  200
```

```yaml
# .github/workflows/deploy.yml  (GitHub Pages needs 404.html = index.html,
# and a `base` in vite.config.ts if served from /<repo>/)
```

**Verify:** open the live site, navigate to a profile, then hard-refresh (⌘⇧R).
If you get a 404, this is unfixed.

## 13b. No social preview metadata

[`client/index.html`](../../client/index.html) has `<title>` and a viewport tag,
and nothing else. Pasting the link into LinkedIn, Twitter, Slack, or Discord —
which is exactly what you do with a portfolio project — produces a bare URL with
no title, no description, no image.

```html
<meta name="description" content="Search any GitHub user or organization and explore their profile, repositories, and contribution history." />
<meta name="theme-color" content="#23272b" />

<meta property="og:type" content="website" />
<meta property="og:title" content="GitHub User Explorer" />
<meta property="og:description" content="Search any GitHub user or organization and explore their profile, repositories, and contribution history." />
<meta property="og:image" content="https://your-domain.app/og-image.png" />
<meta property="og:url" content="https://your-domain.app" />

<meta name="twitter:card" content="summary_large_image" />
```

`og:image` must be an **absolute** URL, 1200×630, and under ~1 MB. A screenshot
of the profile page with the contribution grid is the right choice — it is the
most visually distinctive screen in the app.

## 13c. Theme colour and PWA basics

`<meta name="theme-color">` tints the browser chrome on mobile. Since the app
has a light/dark mode, ship both:

```html
<meta name="theme-color" content="#e0e0e0" media="(prefers-color-scheme: light)" />
<meta name="theme-color" content="#23272b" media="(prefers-color-scheme: dark)" />
```

Those values are the exact backgrounds from
[`muiCustomTheme.ts:16-17`](../../client/src/theme/muiCustomTheme.ts#L16). A
`manifest.webmanifest` with a name, icons, and `display: "standalone"` is another
20 minutes and makes the site installable — optional, but cheap.

## 13d. Flash of wrong theme on load

```tsx
// ModeContextProvider.tsx:6-7
const localStorageValue = localStorage.getItem("mode") as ModeType;
const [mode, setMode] = useState<ModeType>(localStorageValue || "light");
```

The theme is read during React's first render, but the HTML has already painted
with the browser default (white) by then. A dark-mode visitor sees a **white
flash** on every page load.

Fix with a blocking inline script in `<head>`, before the bundle loads:

```html
<script>
  (function () {
    try {
      var m = localStorage.getItem("mode");
      if (m !== "light" && m !== "dark")
        m = matchMedia("(prefers-color-scheme: dark)").matches ? "dark" : "light";
      document.documentElement.dataset.theme = m;
      document.documentElement.style.backgroundColor = m === "dark" ? "#23272b" : "#e0e0e0";
    } catch (e) {}
  })();
</script>
```

Note this needs `script-src 'unsafe-inline'` **or** a CSP hash. Compute the
hash — do not weaken `script-src`, which is the one directive actually doing
work in
[`../vulnerabilities/04.missing-security-headers.md`](../vulnerabilities/04.missing-security-headers.md).

## 13e. No `base` handling for subpath deploys

[`vite.config.ts`](../../client/vite.config.ts) is the default four-line config
with no `base`. Fine for a root-domain deploy; broken on GitHub Pages under
`/github-user-explorer/`. If you ever move hosts, `base` plus React Router's
`basename` both need setting. Worth a comment in the config so the pairing is
not rediscovered under pressure.

## 13f. No caching headers for hashed assets

Vite emits content-hashed filenames (`index-a3f9c2.js`), which are safe to cache
forever. Most hosts get this right by default, but pin it:

```json
{
  "headers": [
    { "source": "/assets/(.*)", "headers": [{ "key": "Cache-Control", "value": "public, max-age=31536000, immutable" }] },
    { "source": "/index.html",  "headers": [{ "key": "Cache-Control", "value": "no-cache" }] }
  ]
}
```

`index.html` must **not** be cached, or visitors keep loading an old bundle
after a deploy.

## Contradictions & trade-offs

- **13d's inline script directly conflicts with the CSP in
  [`../vulnerabilities/04`](../vulnerabilities/04.missing-security-headers.md).**
  Resolution: compute the SHA-256 hash of the script and add
  `'sha256-…'` to `script-src`. Do **not** add `'unsafe-inline'` — that would
  undo the single most valuable directive in the policy.
- **13d also overlaps with
  [`../vulnerabilities/06.untrusted-localstorage.md`](../vulnerabilities/06.untrusted-localstorage.md).**
  The inline script and `readMode()` must agree on validation and on the
  `prefers-color-scheme` fallback, or the pre-paint colour and React's chosen
  theme will disagree — a flash in the opposite direction. Keep the two literal
  values in one place.
- **The one config file has to match the actual host.** `vercel.json` on Netlify
  does nothing, and vice versa. Committing both is confusing; commit the one you
  use and note the alternative in the README.
- **`og:image` adds a ~200 kB asset** that only social crawlers fetch — no
  impact on page load, but it does add repo weight
  ([07.asset-and-bundle-weight.md](07.asset-and-bundle-weight.md)).
- **The single-file config often carries both rewrites and headers.** If you
  implement [`../vulnerabilities/04`](../vulnerabilities/04.missing-security-headers.md)
  and this suggestion separately, you will edit the same file twice — do them
  together.
