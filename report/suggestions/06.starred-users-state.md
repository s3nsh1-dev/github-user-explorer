## 6a. Two independent providers, two independent states

```tsx
// client/src/components/UpperHomeUI.tsx:17
<StaredUserContextProvider><StaredRepositories /></StaredUserContextProvider>

// client/src/page/ProfileInfo.tsx:120
<StaredUserContextProvider><UserProfileHeader userProfile={userProfile} /></StaredUserContextProvider>
```

Two separate provider instances with two separate `useState` stores. They are
never mounted simultaneously (different routes), so today they agree — but only
because each one re-reads `localStorage` on mount, and `localStorage` is doing
the actual state-sharing that context is supposed to do.

The provider is a pass-through wrapper around browser storage. That is not what
context is for, and the moment both mount at once (add a starred-count badge to
the navbar, for instance) they diverge silently.

**Fix:** hoist it once, next to the other provider:

```tsx
// client/src/main.tsx
<ModeContextProvider>
  <StaredUserContextProvider>
    <QueryClientProvider client={queryClient}>
      <BrowserRouter><App /></BrowserRouter>
    </QueryClientProvider>
  </StaredUserContextProvider>
</ModeContextProvider>
```

Then delete the two nested wrappers. `UpperHomeUI` becomes a plain layout box,
and `ProfileInfo` loses a level of nesting.

## 6b. `localStorage` is read on every single render

```tsx
// client/src/context/StaredUserContextProvider.tsx:9-12
const initialList: string[] = JSON.parse(
  window.localStorage.getItem("staredProfiles") || "[]"
);
const [staredList, setStaredList] = useState<string[]>(initialList);
```

`initialList` is a plain `const` in the component body — recomputed on **every
render**, running a synchronous storage read and a `JSON.parse` each time. The
value is then passed to `useState`, which ignores it after the first render, so
the work is pure waste.

`useState` accepts a lazy initialiser for exactly this:

```tsx
const [staredList, setStaredList] = useState<string[]>(readStarred);   // called once
```

## 6c. `checkStared` reads storage instead of state

```tsx
// lines 22-24
const checkStared = (value: string) => initialList.includes(value);

// lines 34-40
const updateStaredList = (value: string) => {
  if (initialList.includes(value)) removeStaredUser(value);
  else addStaredUser(value);
};
```

Both consult `initialList` — the storage snapshot — rather than `staredList`,
the state React actually renders from. It happens to work because the write is
synchronous inside the updater (6d) and `initialList` is recomputed each render
(6b), so the two stay in step.

That is three bugs cancelling out. Any one of the individually-correct fixes
above breaks the balance: fix 6b alone (lazy `useState`) and `initialList`
freezes at its mount value — **the star icon then stops toggling**, because
`checkStared` keeps returning the original answer.

**So 6b and 6c must be fixed together.** Read from state:

```tsx
const checkStared = (value: string) => staredList.includes(value);
const updateStaredList = (value: string) =>
  setStaredList((prev) =>
    prev.includes(value) ? prev.filter((v) => v !== value) : [...prev, value]
  );
```

## 6d. Side effects inside a state updater

```tsx
// lines 14-20
setStaredList((prev) => {
  const updated = [...prev, value];
  window.localStorage.setItem("staredProfiles", JSON.stringify(updated));  // ← effect
  return updated;
});
```

React requires updaters to be pure and may invoke them more than once —
`StrictMode` is on ([`main.tsx:12`](../../client/src/main.tsx#L12)), so in
development this write **does** run twice per click. It is idempotent, so
nothing corrupts today. Move it to an effect:

```tsx
useEffect(() => { writeStarred(staredList); }, [staredList]);
```

## 6e. Two hooks, two different null contracts

```ts
// useMode.ts:6-8         → throws when the context is missing
if (!modeContext) throw new Error("Mode Context is null");

// useStaredUserList.ts:6-9 → returns null when the context is missing
if (!starUserContext) return null;
```

The `null` return forces optional chaining at every call site
(`staredContext?.updateStaredList(...)`,
[`UserProfileHeader.tsx:51`](../../client/src/components/UserProfileHeader.tsx#L51))
and turns a wiring mistake into a **silently non-functional star button** rather
than a loud error. Make both throw. Once the provider is at the root (6a), the
`null` case cannot legitimately occur.

## 6f. Naming

`stared` → `starred` (one r vs two), `StaredRepositories` actually renders
starred **users**, and `useStaredUserList` is the file name while the export is
`useStartedUserList` — "started", a third spelling. Rename while the surface is
small: `StarredUsersProvider`, `useStarredUsers`, `StarredUsersMenu`. A reviewer
reading three spellings of one concept in four files draws conclusions.

## Contradictions & trade-offs

- **6b and 6c are individually breaking and jointly correct.** Fixing the lazy
  initialiser without switching `checkStared` to state leaves the star button
  permanently stuck. Treat them as one commit.
- **Hoisting the provider changes when storage is read** — once at app start
  instead of on each page mount. If a second tab stars a profile, this tab no
  longer picks it up on navigation. Add a `storage` event listener if you care
  about cross-tab sync; for this app, probably not worth it, but the behaviour
  *does* change.
- **Overlaps with [`../vulnerabilities/06.untrusted-localstorage.md`](../vulnerabilities/06.untrusted-localstorage.md)**,
  which rewrites the same lines for validation. Same file, same functions — one
  pass, not two.
- **The rename touches nine files and every import.** Do it in an isolated
  commit with no behavioural change, so the diff stays reviewable.
- **`selectValue` in `StaredRepositories`
  ([line 15](../../client/src/components/StaredRepositories.tsx#L15)) is local
  state that mirrors the current route.** After navigating it shows the last
  clicked user forever, even after you navigate elsewhere. Derive it from
  `useParams()` instead of storing it — or drop it and always show the chevron.
