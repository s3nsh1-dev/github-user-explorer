## Issue 1 — where the blank stage came from

### What was reported

> The flow is: **1.** placeholder UI (good) → **2.** the placeholder vanishes and
> the space is empty (bad) → **3.** the placeholder renders again for a few ms,
> then the graph (good). Stage 3 should follow stage 1 directly. Where is
> stage 2 coming from?

Exactly right, and the instinct that stage 2 does not belong was correct.

### The cause

**A profile page makes three requests, one after another, and only two of them
had a placeholder.**

```
GET /api/users?login=…          → ProfileInfo renders <ProfileSkeleton>   ← stage 1
GET /api/owner-type?login=…     → ContributionChart renders NOTHING       ← stage 2
GET /api/contributions?login=…  → UserContributions renders <LoadingSkeleton>  ← stage 3
```

The middle request exists because the app does not know, until it asks, whether
`/user/:name` is a person or an organization — a person gets the contribution
graph, an organization gets its top repositories. `ContributionChart` is the
component that asks, and it was written like this:

```tsx
const { data } = useFetchLoginType(username);
if (!data) return null;          // ← the entire bug
```

`data` is `undefined` for as long as that request is in flight, so the chart
area rendered **nothing at all** — not a skeleton, not a spinner, just
collapsed space — for one full round trip.

The three requests are **sequential, not parallel**, which is what makes the gap
long enough to see. `ContributionChart` does not mount until the profile query
resolves, and `UserContributions` does not mount until the owner-type query
resolves. So the gap is never shorter than one round trip to GitHub and back.

### Measured, before the fix

Production build, headless Chrome, 250 ms of emulated latency per request and
the HTTP cache disabled, sampling the DOM every 40 ms:

```
   401– 1006 ms  blank page                605 ms
  1052– 1481 ms  profile skeleton          429 ms
  1577– 1840 ms  >>> NOTHING <<<           263 ms   ← stage 2
  1913– 2483 ms  contribution skeleton     570 ms
  2649–       graph

  requests: users 1024–1514 | owner-type 1542–1877 | contributions 1896–2484
```

**The blank window (1577–1840 ms) sits exactly inside the `owner-type` request
(1542–1877 ms).** That is the proof, not an inference — the gap starts when the
request starts and ends when it ends.

### The fix

`ContributionChart` now renders the same skeleton `UserContributions` uses,
instead of `null`:

```tsx
const { data, isLoading, error, refetch } = useFetchLoginType(username);

if (isLoading) return <LoadingSkeleton />;
if (error) return <ErrorState error={error} onRetry={refetch} sx={{ mt: 2 }} />;
if (!data) return null;
```

`isLoading` rather than `isPending`: with React Query v5 a *disabled* query is
pending but not fetching, and `isLoading` is the flag that means "actually
waiting on the network". Using `isPending` here would show a skeleton forever if
the query were ever disabled.

**The error branch is a second bug found on the way.** A failed owner-type
request left `data` undefined permanently, so the chart area was blank with
nothing on screen to retry and no indication anything had gone wrong. It now
renders `<ErrorState>` with its Retry button, like every other failure in the
app.

### Measured, after the fix

Identical conditions, same script:

```
   399– 1007 ms  blank page                608 ms
  1044– 1518 ms  profile skeleton          474 ms
  1633– 2438 ms  contribution skeleton     805 ms
  2636–       graph
```

**The `NOTHING` phase is gone.** The contribution skeleton absorbed it —
570 + 263 ≈ 805 ms — and the time to the finished graph is unchanged
(2649 ms → 2636 ms, i.e. noise). The fix removes a hole; it does not make
anything slower or faster.

### What was deliberately not changed

**The three requests are still sequential.** Making them parallel means starting
the owner-type request before the profile resolves — a prefetch at the route
level, or hoisting the hook into `ProfileInfo`. That would genuinely cut ~300 ms
off the time to the graph, but it is a data-flow change with its own failure
modes, and it is not what was reported. The reported symptom was a hole in the
loading sequence, and the hole is closed. **Worth doing later; noted here so it
is not forgotten.**

## Issue 2 — the counts are back in the cells

### What was reported

> The contribution graph is not showing the number of commits on the circles.
> Previously it did. On hover I can see it, which is nice, but I want the number
> too.

### Why they were removed

P25 (session S8) took them out for a real reason. Every cell painted its count
in `#fffff0` — near-white — on GitHub's colour ramp, whose lightest step is
`#ebedf0`, also near-white. **A zero-contribution day was white text on a white
circle**, and roughly the lightest third of the ramp was unreadable. The plan's
options were "drop the digits" or "compute a per-cell text colour", and it chose
to drop them, calling the alternative "more code for a worse result".

That was the wrong call for this project — the numbers are part of what makes
this graph *this app's* graph rather than a copy of GitHub's.

### The fix

The count is back in every real cell, with the text colour computed **per cell**
from that cell's background:

```ts
const readableOn = (color: string): string => {
  // … WCAG relative luminance of the cell's own colour …
  return onBlack > onWhite ? "#000000" : "#ffffff";
};
```

Same formula the S8 contrast audit used. It picks black for the pale end of the
ramp and white for the dark end, so every cell is readable rather than one
colour being a compromise across all of them.

Three digits do not fit a 20 px circle at the size one digit does, so the type
steps down above 99 (`0.65rem` → `0.5rem`) instead of overflowing.

**Everything from S8 is kept:** the tooltip, the per-cell `aria-label`, the
grid's one-line summary, and `aria-hidden` on the padding cells that square off
a short week — those still render no number, because they are not days.

### Verified

On `/user/torvalds`, both themes, against live GitHub data:

| Check | Result |
|---|---|
| Cells showing a number | **371 of 371** real days |
| Distinct colour pairs actually used | 5 |
| **Worst contrast in the whole grid** | **6.26:1** (white on `#216e39`) — every pair passes 4.5:1 |
| Cells whose text overflows the circle | **0** |
| Padding cells still silent and `aria-hidden` | ✅ |
| Tooltip on hover | ✅ "2 contributions on Thu, 19 Feb 2026" |
| `aria-label` on the same cell | ✅ identical string |
| Grid summary | ✅ "3409 contributions between 2025-08-03 and 2026-08-08. Most active day: 65…" |
| Console errors / CSP violations | **0 / 0** |

Screenshots at 3× in both themes confirm it reads cleanly: black numerals on the
pale greens and on the near-white zero days, white numerals on the dark greens.

## Consequences for the rest of the report

- **`report/suggestions/09.accessibility.md` §9e/§9f** and
  **`report/implementation_plans/P25.contribution-grid-a11y.md`** both record
  "the digits were removed, deliberately". That is now **reversed** — the
  digits are back, and the contrast problem P25 was solving is solved properly
  instead of avoided. The contrast guarantee is *stronger* than it was: it is
  now computed per cell rather than asserted once.
- **`00.INDEX.md`'s "What S8 changed" note says "P26/P27 must not restore the
  digits".** That instruction is withdrawn. What must not come back is a
  *single hard-coded* text colour across the whole ramp.
