## Decisions locked in

- **B2 = keep the contribution graph** → proxy, not token-free. GraphQL requires auth; there is no unauthenticated path to the contribution calendar.
- **B3 = Netlify**, live at <https://github-userexplorer.netlify.app/>

## Confirmed exposure (2026-08-07)

The live bundle `/assets/index-CnEJiIFO.js` (571 KB) contains **4 occurrences of
a `ghp_`-prefixed token**. Verified by fetching the public URL; the value was
not recorded. This is live right now.

## Why Netlify Functions rather than a long-running Express server

- **Same origin** → no CORS config, and `connect-src 'self'` in **P35** becomes trivially correct.
- **No cold-start penalty** on the free tier. A sleeping Render/Railway instance makes the portfolio demo take 10+ seconds on first click — a worse first impression than the bug being fixed.
- The `server/` folder can still hold the shared handler logic so the repo stays honestly "fullstack".

## Steps

### 1. Structure

```
netlify/functions/
  users.mts            → /api/users/:login
  user-repos.mts       → /api/users/:login/repos
  repo.mts             → /api/repos/:owner/:name
  search-users.mts     → /api/search/users
  owner-type.mts       → /api/owner-type/:login       (GraphQL)
  contributions.mts    → /api/contributions/:login    (GraphQL)
  org-repos.mts        → /api/org-repos/:login        (GraphQL)
  _shared/github.mts   → auth, validation, upstream fetch, cache
```

Use Netlify's modern function signature (`.mts`, `export default async (req: Request) => Response`).

### 2. `_shared/github.mts` — the security boundary

Token comes from the Zod-validated `env` module built in **P28** — never
`process.env` directly, so a missing or whitespace-padded value fails at cold
start with a readable message instead of a 401 later:

```ts
import { env } from "./env.mts";   // Zod-validated; env.GITHUB_TOKEN is typed string

const LOGIN = /^[a-zA-Z0-9](?:[a-zA-Z0-9]|-(?=[a-zA-Z0-9])){0,38}$/;
const REPO  = /^[A-Za-z0-9_.-]{1,100}$/;

export const ghREST = (path: string) =>
  fetch(`https://api.github.com${path}`, {
    headers: {
      Accept: "application/vnd.github+json",
      "X-GitHub-Api-Version": "2022-11-28",
      Authorization: `Bearer ${env.GITHUB_TOKEN}`,   // ← NO VITE_ PREFIX. That prefix caused this bug.
    },
  });

export const ghGraphQL = (query: string, variables: Record<string, unknown>) =>
  fetch("https://api.github.com/graphql", {
    method: "POST",
    headers: { Authorization: `Bearer ${env.GITHUB_TOKEN}`, "Content-Type": "application/json" },
    body: JSON.stringify({ query, variables }),
  });
```

**Four non-negotiables. Every one of these is a way to reintroduce the bug with a secret behind it:**

1. **GraphQL query documents live server-side.** The client sends `{ login }`, never a `query` string. A proxy that forwards a client-supplied document is exactly as vulnerable as today's code. Move the constants from `client/src/constants/graphqlQueries.ts` (**P08**) into `netlify/functions/_shared/queries.mts`.
2. **Validate `:login` / `:name` against the regexes above, then `encodeURIComponent` anyway.** Belt and braces — see [vulnerabilities/03](../vulnerabilities/03.api-url-tampering.md).
3. **Allow-list the endpoints.** No generic `/api/gh/*path` passthrough — that is endpoint redirection with a live token.
4. **Never forward upstream error bodies.** Map to `{ error: "not_found" | "rate_limited" | "upstream_error" }` + a status. Forwarding reopens [vulnerabilities/09](../vulnerabilities/09.error-message-disclosure.md) with a secret behind it.

### 3. Caching — required, not optional

All visitors now share one token, so the 5,000/hr limit becomes a single pool
([vulnerabilities/07](../vulnerabilities/07.rate-limit-exhaustion.md)). Set on
every successful response:

```ts
"Cache-Control": "public, max-age=300, s-maxage=300"
```

Netlify's CDN honours `s-maxage`, so repeat requests for the same profile never
reach GitHub. Also forward the upstream `x-ratelimit-*` headers through so the
client's `RateLimitError` (**P05**) still works.

### 4. `netlify.toml` — function + redirect wiring

```toml
[build]
  base    = "client"
  command = "npm run build"
  publish = "dist"

[functions]
  directory  = "../netlify/functions"
  node_bundler = "esbuild"

[[redirects]]
  from = "/api/*"
  to   = "/.netlify/functions/:splat"
  status = 200
```

⚠️ **`base = "client"` makes every other path in this file relative to
`client/`** — hence `../netlify/functions`. This is the single most common
Netlify misconfiguration. Verify the functions actually deploy before assuming.

*(The headers and SPA-fallback blocks go in the same file — **P35**. Coordinate
so we do not fight over it.)*

### 5. Client migration

`githubFetch` / `githubGraphQL` from **P05** change URL only — this is exactly
why P05 centralised the token read into one file:

```ts
// client/src/helper/githubFetch.ts
const API = "/api";
// Authorization header: DELETED
// import.meta.env read: DELETED
```

Dev proxy so `npm run dev` still works:

```ts
// client/vite.config.ts
server: { proxy: { "/api": "http://localhost:8888" } },   // netlify dev's port
```

Run `npx netlify dev` locally to serve functions + client together.

### 6. Your two manual actions

1. **Netlify → Site settings → Environment variables → add `GITHUB_TOKEN`** (a *new* token, no scopes — public data needs none). The local `.env.development` covers `netlify dev` only; Netlify's build/runtime does not read it.
2. **Revoke the old token** at <https://github.com/settings/tokens>. It is public; assume it is compromised.

### 7. Current state to expect when starting (verified 2026-08-07)

- The client **still reads `VITE_GITHUB_AUTHENTICATION_TOKEN` in all 8 hooks** and still sends 9 `Authorization` headers. Removing the variable's *definition* did not change the *code* — that removal is this plan's step 5.
- The site is therefore **currently broken** (requests go out with `Bearer undefined`). Expected, and acceptable — zero traffic.
- `.env.development` exists at the repo root with `GITHUB_TOKEN`, correctly gitignored, untracked. ⚠️ **Its key has a trailing space (`GITHUB_TOKEN =`)** — fix in **P28** before wiring anything, or `process.env.GITHUB_TOKEN` may come back `undefined` depending on the parser.
- Root `package.json` / `package-lock.json` are deleted on disk (unstaged). That happens to resolve the phantom-dependency-tree finding in [vulnerabilities/10](../vulnerabilities/10.secret-and-dependency-hygiene.md) §10b — but the deletion still needs committing.

## Acceptance criteria

- [ ] `grep -rn "import.meta.env\|Authorization\|VITE_" client/src` → **no hits** (all 8 hooks + 9 headers gone)
- [ ] Missing/whitespace-padded `GITHUB_TOKEN` → readable Zod startup error naming the field, value never logged
- [ ] Fresh production build: `grep -cE '(ghp|github_pat|gho|ghs)_' dist/assets/*.js` → **0**
- [ ] Re-run the live-site check after deploy → 0 matches
- [ ] All 7 endpoints return correct data via `netlify dev`
- [ ] Contribution graph still renders (the whole point of B2)
- [ ] `POST /api/owner-type/x` with a body containing a `query` field → ignored, not executed
- [ ] `/api/users/x%2F..%2F..%2Forgs%2Fgithub` → 400, not a redirected upstream call
- [ ] Second request for the same profile is a CDN cache hit
- [ ] Verification gate green

## Do NOT

- Do not use a `VITE_` prefixed variable anywhere in the function code. That prefix is the entire bug.
- Do not accept a client-supplied GraphQL document, under any framing.
- Do not add a catch-all passthrough route.
- Do not forward upstream error bodies to the client.
- Do not deploy before the `GITHUB_TOKEN` env var exists in Netlify — the site will 500 on every request.
- Do not delete the old token before the new one is confirmed working, or the live site breaks in between.
