## Why — this is a confirmed, user-visible bug on the app's main page

```tsx
// client/src/page/ProfileInfo.tsx:49-52
if (!userData) return null;                                    // ← runs first
const userProfile = mapGitHubResponse(userData as GitHubApiUser);
if (userLoading) return <div>Loading...</div>;                 // ← unreachable
if (userError) return <div>Error: {userError.message}</div>;   // ← unreachable
```

While loading, `userData` is `undefined` → returns `null` → **the loading branch
can never run**. On failure `userData` is also `undefined` → **the error branch
can never run either**. The visitor gets a blank page under the navbar, during
every load and permanently after any failure.

## Steps

### 1. Reproduce first

- Throttle to Slow 3G, load a profile → confirm blank, no spinner.
- Load `/user/zzzz-not-a-real-user-zzzz` → confirm blank, no error message.

### 2. Reorder to match the states that actually occur

```tsx
const { data, isLoading, error, refetch } = useFetchUserData({ username });

if (isLoading) return <ProfileSkeleton />;
if (error)     return <ErrorState error={error} onRetry={refetch} />;
if (!data)     return <NotFound title="User not found" />;   // ← placeholder until P16

const userProfile = mapGitHubResponse(data);
```

`mapGitHubResponse` must run **after** the guards — currently it runs on line 50,
before the error check, so a malformed payload throws there instead of being
reported.

### 3. Add `ProfileSkeleton`

`client/src/components/skeletons/ProfileSkeleton.tsx` — mirror the real layout
(avatar circle, name bar, 8 detail rows, contribution grid) using MUI
`<Skeleton>`. Matching the final layout prevents the layout shift that a bare
`<CircularProgress />` in an 80vh box guarantees.

### 4. Same ordering audit in the sibling components

Check `DisplayRepoList` and `ShowSelectedRepo` for the same inverted pattern
while I am here. `ShowSelectedRepo` looks correct already (`isLoading` → `error`
→ `!repo`) — verify, don't assume.
