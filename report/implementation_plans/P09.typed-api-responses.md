## Why

`Response.json()` returns `Promise<any>`, and 7 of 8 hooks pass no generic to
`useQuery`. So every piece of API data in the app is `any`, and `strict: true`
in [`tsconfig.app.json`](../../client/tsconfig.app.json) sees none of it.

Concrete cost: the `NaN` bug in **P15** compiles cleanly today, because
`data?.public_repos` is `any` and `any` is assignable to `number`.

`githubFetch<T>` from **P05** already takes a generic — this plan supplies the
type arguments and fixes the wrong types it exposes.

### 6. Validate with Zod, and derive the types from the schemas — **B9 answered: yes**

`zod` is installed in **P28**. Schemas replace hand-written interfaces, so the
type and the check cannot disagree:

```ts
// client/src/constants/schemas.ts
import { z } from "zod";

export const GitHubApiUserSchema = z.object({
  login: z.string(),
  node_id: z.string(),
  avatar_url: z.string().url(),
  html_url: z.string().url(),
  name: z.string().nullish(),
  bio: z.string().nullish(),
  company: z.string().nullish(),
  location: z.string().nullish(),
  blog: z.string().nullish(),
  email: z.string().nullish(),
  twitter_username: z.string().nullish(),
  hireable: z.boolean().nullish(),          // GitHub returns null for most accounts
  type: z.enum(["User", "Organization"]),
  created_at: z.string(),
  updated_at: z.string(),
  followers: z.number(),
  following: z.number(),
  public_repos: z.number(),
  public_gists: z.number(),
  repos_url: z.string(),
  followers_url: z.string(),
  following_url: z.string(),
  starred_url: z.string(),
});

export type GitHubApiUser = z.infer<typeof GitHubApiUserSchema>;   // ← derived, not duplicated
```

Wire into `githubFetch` as an optional validator so every hook opts in:

```ts
export async function githubFetch<T>(url: string | URL, schema?: z.ZodType<T>): Promise<T> {
  const res = await fetch(url, { headers: authHeaders() });
  assertOk(res);
  const json = await res.json();
  if (!schema) return json as T;

  const parsed = schema.safeParse(json);
  if (!parsed.success) {
    if (import.meta.env.DEV) console.error("Schema mismatch:", parsed.error.issues);
    throw new GitHubError("Unexpected response shape from GitHub");
  }
  return parsed.data;
}
```

**Use `.safeParse`, never `.parse`.** A schema gap must degrade into a handled
error (rendered by **P13**'s `ErrorState`), not an uncaught throw. And the
user-facing message stays generic — issue detail goes to the console only, per
[vulnerabilities/09](../vulnerabilities/09.error-message-disclosure.md).

**Be liberal with `.nullish()`** on optional profile fields. `blog`, `company`,
`email`, and `twitter_username` are `null` *or absent* depending on the account;
a too-strict schema rejects users GitHub returns happily. Test against a sparse
account (a brand-new user) and a rich one (`torvalds`) before calling this done.

Schemas needed: `GitHubApiUserSchema`, `RepoSchema`, `RepoListSchema`,
`UserSearchResultSchema`, plus the three GraphQL payload schemas.

## Do NOT

- **Do not use `.parse()`** — always `.safeParse()`. An unhandled throw from a schema gap is a white screen.
- **Do not write a type and a schema separately.** Always `z.infer<typeof Schema>`; two sources of truth drift, which is the whole problem being fixed.
- Do not schema-validate in the *functions* as well as the client. Validate once, at the client boundary. **P34** validates *inputs* (login/repo names), not GitHub's output.
- Do not add GraphQL codegen. Three queries; hand-written types are proportionate.
- Do not "fix" the type errors this surfaces by widening types or adding `as`. If real types surface a real bug, that is the point — fix the bug or note it and stop. Expect the first `tsc` run after this to fail in several files.
- Do not rename `hirable` → `hireable` on the *view model* here. That is **P19**'s rename batch; only the API-side `hireable` type is in scope.
